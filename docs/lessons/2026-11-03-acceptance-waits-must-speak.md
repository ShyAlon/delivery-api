# Every acceptance wait must say what it is waiting for

A plan followed by several minutes of silence is not useful evidence of a healthy run. The real owner journey launches a headless verification browser, creates a test task, submits Start, waits for the first text question, submits the scripted answer and waits for a second text question. Both question waits have a900second deadline, with2second polling. Every HTTP operation has a90second timeout. Structured decisions are refused rather than left for an invisible human.

The script now prints a stage immediately and a heartbeat every10seconds, with total/stage elapsed time, question deadline or explicit per-operation timeout, and fixed server state names. It prints the created task ID and view URL immediately. No question, answer, cookie, token or provider response is copied into these lines.

Interrupting this client does not Stop server work. Catch KeyboardInterrupt long enough to retain the task reference and failure evidence and say that accepted work may still bill. Do not automatically Stop, purge, retry or create a second task. The owner can review the identified task in Worker Jobs and confirm Stop there.

A subsequent owner run returned ReadTimeout after accepted Start. Historical output discarded method/path, so the exact failed call cannot be inferred without its captured server evidence. Transport errors now preserve safe method/path, exception class and request timeout, never raw exception text. Only read-only task polls retry on transport uncertainty within the original deadline. Start and answer are never replayed after an unknown response. Hidden browser navigation, evidence checks and question waits are named; answers are explicitly API submissions, not invented browser clicks.
